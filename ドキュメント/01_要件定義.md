# 01_要件定義

## 1. 背景・目的

- クレジットカード（三井住友 / AMEX）を家族（A・B）で共有している。
- 毎月の利用明細を1件ずつ確認し、「Aの支払い」「Bの支払い」「二人で支払い（共同）」の3区分に振り分けて、それぞれの月次合計・推移を把握したい。
- 既存の類似アプリ「クレカ支払い振り分け」（FastAPI + SQLite、ローカル専用）とは別に、**GitHub Pages で公開しスマホからも操作できる版**を新規に作る。
- 既存アプリの運用で判明した使い勝手上の改善点（矢印キー操作、文字サイズ、月別グループ表示など）は、後回しにせず本バージョンの要件に最初から含める。

## 2. 利用者・利用シーン

- 操作者は**本人（1名）のみ**。A・Bそれぞれが自分の端末から振り分け操作を行うことは想定しない。
- 月に一度程度、スマホまたはPCのブラウザから明細CSVを取り込み、その場で1件ずつ振り分ける。
- 自宅Wi-Fi以外のネットワーク（外出先の4G/5G等）からもアクセスできる必要がある（GitHub Pagesで公開するため満たされる）。

## 3. 対象CSVフォーマット

`参考/` フォルダにある2種類の明細に対応する。**カード種別の判定はファイル名ではなく、CSVの中身（ヘッダー構造）で行う**（既存プロジェクトのファイル名判定方式とは異なる方式を採用）。

### 3.1 三井住友カード形式（例: `202607.csv`）

- 文字コード: Shift-JIS
- ヘッダー行なし。1行目は `会員名様,カード番号,カード券面名称` の3項目（例: `上柳　太一　様,4980-00**-****-****,三井住友ゴールドＶＩＳＡ（ＮＬ）`）。
- 明細行: `利用日,利用先,金額,数量,数量,金額(同額),備考`
- 1ファイル内に「会員名様,カード番号,...」形式の行が複数回出現し得る（家族カード分の明細が続けて記載される）＝ 1ファイルに複数カード会員の明細が混在する。
- 末尾に合計行（日付・利用先が空で金額のみの行）がある。

### 3.2 AMEX形式（例: `A202606.csv`）

- 文字コード: Shift-JIS
- 1行目がヘッダー行: `ご利用日,データ処理日,ご利用内容,カード会員様名,会員番号 #,金額,海外通貨利用金額,換算レート`
- 明細行ごとに「カード会員様名」列があり、家族カード利用者名（例: `TAICHI UEYANAGI` / `AYAKA UEYANAGI`）が入る＝ 1ファイルに複数カード会員の明細が混在する。

### 3.3 判定ロジック（設計時に詳細化）

- 1行目がAMEXのヘッダー文字列と一致する → AMEX形式
- 1行目が `◯◯様,カード番号,...` のパターン（末尾が「様」を含む名義＋カード番号）→ 三井住友形式
- どちらにも一致しない場合は取込エラーとしてユーザーに通知する。

### 3.4 取り込み方法

- スマホのファイルアプリ等に保存されたCSVファイルを、ブラウザのファイル選択（`<input type="file">`）で読み込む。ドラッグ&ドロップは必須としない。
- サーバーを介さず、ブラウザ内（JavaScript）でCSVをパースする。

## 4. 機能要件

### 4.1 CSV取込

- 3.1/3.2の2形式を自動判定して取り込む。
- 取込前に、同一ファイルの重複取込（同一年月・同一カード種別の再取込）を検知し、確認を求める。
- 1ファイルに複数カード会員の明細が混在する場合も、全明細を個別レコードとして取り込む（カード会員名はA/B/共同の振り分けの参考情報として保持するが、自動での振り分け確定は行わない＝振り分けは必ずユーザー操作で行う）。

### 4.2 自動振り分け機能

- CSV取込のタイミングで、明細の「項目名」（三井住友形式は利用先、AMEX形式はご利用内容）に登録済みキーワードが含まれるかを判定し、一致すればA単体／B単体／共同のいずれかへ**自動的に振り分ける**。
- キーワードと振り分け先（A単体／B単体／共同）の対応ルールは、**アプリ内のルール管理画面で追加・編集・削除**できるようにする。
- ルールもlocalStorage/IndexedDBに保存する（4.5節のデータ管理対象に含む）。
- ルールに一致した明細は、確認用の中間状態を経ずにそのまま**「振り分け済み」として確定**する（未振り分け一覧には出さない）。
  - ただし振り分け済み一覧から見て、どの明細が自動振り分けによるものかは区別できるようにする（例: 「自動」バッジ表示）。
  - 自動振り分け結果は4.3節（振り分け操作）と同様、後から手動で修正できる。
- 複数のルールが同じ明細に一致する場合の優先順位（例: 登録順・後勝ちなど）は設計時に定める。
- ルールに一致しなかった明細は、従来どおり未振り分けとして4.3節の手動振り分け操作の対象になる。

### 4.3 振り分け操作（メイン操作）

- 未振り分けの明細を1件ずつ表示し、「Aの支払い」「Bの支払い」「二人で支払い（共同）」の3択から選択する。
- タップ／クリックに加えて、**矢印キー（←/→）でもA単体・二人（共同）を選択できる**（片手・キーボード操作のしやすさを重視）。
- ボタン・文字サイズは大きめにし、スマホでの誤タップを防ぐ。
- 未振り分け一覧・振り分け済み一覧は、**月ごとにグループ化して表示**する。
- 各明細の利用日は**年も含めて表示**する（年をまたぐ利用明細の混同を防ぐ）。
- 振り分けは後から変更可能とする。

### 4.4 集計・レポート

- 月ごとに「Aの支払い合計」「Bの支払い合計」「二人の支払い合計」を集計する。
- 集計表示は以下の3グループに分けて表示する。
  1. 二人の合計・一人当たり金額（二人の合計 ÷ 2）
  2. Aの支払い合計
  3. Bの支払い合計
- 「二人の合計」は月次推移をグラフで表示する。
- 推移グラフとは別に、**最新月の値を目立つ形で強調表示**する（過去の累計より、直近月の金額を最優先で把握したいというニーズに対応）。
- 集計画面で特定の月を選択すると、その月の振り分け済みレコード一覧を表示する（ドリルダウン）。

### 4.5 データ管理

- 振り分け結果、取込済みCSVの履歴（重複防止用）、自動振り分けルールは、**ブラウザのlocalStorage / IndexedDBにのみ保存**する（サーバー・外部DBは使用しない）。
- そのため、データは取り込み・操作を行った**その端末・ブラウザ内に閉じる**（PCとスマホなど複数端末間でのデータ同期は行わない）。
- 誤操作によるデータ消失に備え、**データのエクスポート（JSON等でのバックアップ）／インポート（復元）機能**を用意する。

## 5. 非機能要件

- **完全フロントエンドで動作する静的Webアプリ**として実装する（サーバーサイド処理なし）。GitHub Pagesでそのまま公開できること。
- スマートフォンのブラウザ（Safari/Chrome想定）幅でも操作しやすいレスポンシブレイアウトとする。
- 認証・アクセス制限は設けない。公開URLを知っている人はアクセス可能（URLの非公開性のみに依存する）。ただし振り分け結果自体はブラウザローカルに保存されるため、**URLにアクセスされてもデータそのものが漏洩するわけではない**。

## 6. スコープ外（今回は対応しない）

- 複数端末・複数ブラウザ間でのデータ同期／リアルタイム共有
- A・Bそれぞれが個別にログインして操作する仕組み（ユーザー認証・アカウント管理）
- サーバーサイドでのデータ永続化（DB・API）
- CSV形式以外の明細取込（PDF等）

## 7. 今回の要確認事項と決定内容（サマリ）

| 論点 | 決定内容 |
|---|---|
| データ保存・共有方法 | ブラウザのlocalStorage/IndexedDBのみ。端末間同期なし |
| 振り分け操作を行う人 | 本人1人がまとめて行う |
| カード種別の判定方法 | ファイル名ではなくCSVの中身（ヘッダー構造）で判定 |
| アクセス制限 | 設けない（URLの非公開性のみに依存） |
| 既知の改善点の反映タイミング | 後工程の「変更対応」フェーズを待たず、最初からv1要件に含める |
| 自動振り分けルールの管理方法 | アプリ内のルール編集画面で、ユーザーがキーワード→区分の対応を追加・編集・削除できるようにする |
| 自動振り分け結果の扱い | 中間確認state を設けず、ルール一致は即「振り分け済み」確定（自動である旨は識別表示） |
| CSVファイルの選択方法 | スマホ本体のファイル保存場所から選ぶ標準のファイル選択画面（`<input type="file">`）。3.4節と同一 |
